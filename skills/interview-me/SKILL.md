# Interview Me

## Purpose

Turn real engineering and architecture work into structured interview preparation.

The skill should help the engineer explain:

- what was built
- why decisions were made
- which trade-offs existed
- how risks were handled
- what alternatives were considered
- what an architect should learn from the work

Use actual project experience wherever available rather than generic textbook scenarios.

## When to Use

Use after:

- an architectural decision
- completing a feature
- architecture review
- production incident
- migration
- security decision
- significant engineering trade-off

It may also be used explicitly for interview practice.

## Modes

Supported modes:

```text
architecture
system-design
technical
behavioural
grill
executive
```

### architecture

Focus on architectural reasoning and trade-offs.

### system-design

Turn the implementation into a broader system-design exercise.

### technical

Probe implementation and technology understanding.

### behavioural

Translate experience into STAR-style evidence.

### grill

Act as a demanding interviewer and challenge weak or superficial answers.

### executive

Practice explaining the decision to senior technical or business leadership.

## Workflow

### 1. Establish the Scenario

Determine:

- business problem
- architecture context
- constraints
- engineer's role
- outcome

Do not invent achievements that did not occur.

### 2. Identify Learning Themes

Extract relevant concepts such as:

- architecture trade-offs
- distributed systems
- security
- scalability
- data
- cloud
- integration
- operational readiness
- DevOps
- AI-assisted engineering
- governance

### 3. Ask One Question at a Time

Prefer realistic interview interaction.

Do not immediately provide the answer unless the user requests teaching mode.

### 4. Evaluate the Answer

Assess:

- correctness
- structure
- depth
- architectural reasoning
- communication
- evidence
- trade-off awareness

### 5. Challenge Weak Areas

Use follow-ups such as:

```text
Why?
Why not the alternative?
What breaks first?
How does this fail?
How would you scale it?
How would you secure it?
How would you migrate it?
How would you operate it?
What would you change now?
```

Do not challenge merely for difficulty.

### 6. Teach from the Work

After evaluation, explain important concepts the scenario demonstrates.

Connect implementation details to architecture principles.

### 7. Improve the Answer

When useful, propose a stronger answer structure without fabricating experience.

## Architecture Interview Model

Strong answers should normally demonstrate:

```text
Context
↓
Architectural drivers
↓
Options
↓
Decision
↓
Trade-offs
↓
Implementation
↓
Validation
↓
Outcome
↓
Lessons
```

## Behavioural Interview Model

For behavioural questions use:

```text
Situation
Task
Action
Result
Learning
```

Emphasise the user's own contribution.

## AI Architect Learning

Where relevant, identify how the work demonstrates modern AI Architect responsibilities such as:

- defining engineering standards
- creating agent guardrails
- human-in-the-loop governance
- AI-assisted SDLC design
- quality gates
- security controls
- agent portability
- evaluation and observability
- organisational engineering transformation

Avoid portraying prompt-writing alone as AI architecture.

## Output Modes

When reviewing an answer return:

### Assessment

Short evaluation.

### What Was Strong

Specific strengths.

### What Needs Improvement

Material gaps.

### Stronger Reasoning

Explain missing architectural concepts.

### Improved Answer

Provide an interview-ready version when requested.

### Follow-Up Question

Continue the interview with one meaningful question.

## Behaviour Rules

Do not:

- fabricate experience
- inflate responsibility
- convert every answer into generic architecture terminology
- reward buzzwords without reasoning
- assume one technology is universally correct

Prefer specific engineering evidence over abstract claims.

## Completion Criteria

The exercise succeeds when the user can explain:

- the problem
- the architectural drivers
- the chosen approach
- rejected alternatives
- important trade-offs
- production implications
- lessons learned

without relying on memorised buzzwords.
