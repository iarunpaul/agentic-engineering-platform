# Control Evidence Contract

## Purpose

Define the common logical structure for evidence generated by engineering controls.

The contract allows different tools, CI systems, scanners, review workflows and AI agents to produce evidence in a consistent form.

The evidence contract is independent of the tool that generated it.

## Core Principle

> Evidence describes what was actually verified.

Evidence must not claim stronger assurance than the underlying control execution provides.

## Required Fields

Every evidence record must identify the following.

### controlId

The stable organisational control identifier.

Example:

```text
SEC-001
```

The control ID must exist in:

```text
controls/catalog.yaml
```

### timestamp

The time at which the control execution completed.

Use an unambiguous machine-readable timestamp such as ISO 8601.

Example:

```text
2026-10-04T10:30:00Z
```

### status

One of:

```text
PASS
FAIL
WARN
NOT_APPLICABLE
NOT_EXECUTED
```

#### PASS

The control was executed and satisfied its acceptance criteria.

#### FAIL

The control was executed and did not satisfy its acceptance criteria.

#### WARN

The control identified a non-blocking issue requiring attention.

#### NOT_APPLICABLE

The control does not apply to the evaluated subject.

Where applicability would normally be expected, the reason should be recorded.

#### NOT_EXECUTED

The control applies but was not executed.

`NOT_EXECUTED` must never be interpreted as `PASS`.

### subject

The item being evaluated.

The subject must contain:

```text
type
value
```

Example:

```text
type: commit
value: a83de1f
```

Possible subject types include:

```text
commit
pull-request
artifact
container-image
architecture-change
release
deployment
production-change
```

### source

The mechanism that produced the evidence.

Typical values include:

```text
local
ci
scanner
review
approval-system
deployment-system
agent
other
```

## Recommended Fields

### repository

Repository containing the evaluated change.

### commit

Source commit identifier.

### branch

Source branch where relevant.

### runId

Identifier of the CI workflow, scanner run or control execution.

### tool

Tool used to perform the control.

Example:

```text
controlId: SEC-001
tool: gitleaks
```

The organisational control remains independent of this implementation choice.

### toolVersion

Version of the execution tool where available.

### summary

Short human-readable explanation of the result.

### evidenceUri

Location of detailed evidence where available.

Examples include:

```text
CI artifact
scanner report
test report
pull-request review
deployment record
approval record
```

### metadata

Control-specific structured information.

Examples include:

- number of tests executed
- vulnerabilities found
- severity counts
- artifact digest
- deployment environment
- approval conditions

## Security Control Example

```json
{
  "controlId": "SEC-001",
  "timestamp": "2026-10-04T10:32:00Z",
  "status": "PASS",
  "subject": {
    "type": "commit",
    "value": "a83de1f"
  },
  "source": "scanner",
  "repository": "agentic-engineering-platform",
  "commit": "a83de1f",
  "tool": "secret-scanner",
  "summary": "No committed secrets detected."
}
```

## Review Evidence

Human or agent-assisted review controls use the same logical model.

Example:

```json
{
  "controlId": "ARC-002",
  "timestamp": "2026-10-04T10:35:00Z",
  "status": "PASS",
  "subject": {
    "type": "architecture-change",
    "value": "multi-tenant-data-isolation"
  },
  "source": "review",
  "summary": "Architecture approved with no blocking findings.",
  "metadata": {
    "decision": "APPROVE"
  }
}
```

Review evidence should capture:

- decision
- material findings
- unresolved conditions
- subject reviewed

It does not need to preserve every conversation that occurred during the review.

## Approval Evidence

Approval controls must produce explicit evidence.

Example:

```json
{
  "controlId": "REL-005",
  "timestamp": "2026-10-04T10:40:00Z",
  "status": "PASS",
  "subject": {
    "type": "deployment",
    "value": "release-1.3.0"
  },
  "source": "approval-system",
  "summary": "Production deployment approved.",
  "metadata": {
    "environment": "production"
  }
}
```

Approval must not be inferred from:

- repository access
- tool permissions
- previous approvals
- absence of objection

## Exception Evidence

Approved control exceptions must remain distinguishable from successful control execution.

For example:

```text
SEC-003 = FAIL
GOV-002 = PASS
```

means:

- the security control failed
- an authorised exception was approved

It must not be rewritten as:

```text
SEC-003 = PASS
```

Exception evidence should record:

- affected control
- reason
- scope
- risk
- approver
- expiry where appropriate
- remediation plan where applicable

## Evidence Validation

Evidence intended for automated consumption should conform to:

```text
evidence/schema/control-evidence.schema.json
```

The governance control:

```text
GOV-003 Evidence Validation
```

should eventually validate evidence before release decisions are made.

Validation should ensure:

- control ID is recognised
- required fields are present
- status is valid
- subject is identifiable
- evidence matches the intended control execution
- `NOT_EXECUTED` is not treated as `PASS`

## Evidence Integrity

Evidence should be produced by the system performing the verification wherever practical.

Preferred:

```text
Control execution
      ↓
Machine-readable result
      ↓
Evidence record
```

Avoid:

```text
Agent assumption
      ↓
PASS
```

AI agents may transform or summarise evidence.

They must not manufacture it.

## Tool Independence

Evidence must remain independent of a particular vendor.

For example:

```text
SEC-001 Secret Detection
```

may initially be implemented by one scanner and later another.

The control and evidence contract should remain stable.

Tool information belongs in:

```text
tool
toolVersion
metadata
```

## Evidence Lifecycle

The intended lifecycle is:

```text
Control Selected
      ↓
Control Executed
      ↓
Result Produced
      ↓
Evidence Created
      ↓
Evidence Validated
      ↓
Gate Evaluated
      ↓
Proceed / Block / Exception
```

## Phase 0

Phase 0 initially applies the evidence contract to:

```text
ENG-001  Build Verification
ENG-003  Formatting / Linting
TST-001  Automated Test Execution
SEC-001  Secret Detection
SEC-002  Dependency Vulnerability Scan
```

The contract should evolve only when real control implementations demonstrate a need for additional fields or semantics.
